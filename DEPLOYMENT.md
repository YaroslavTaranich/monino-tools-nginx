# Деплой и восстановление Monino Tools

## Требования

- Docker с Compose v2;
- заполненный `.env` на основе `.env.example`;
- DNS и сертификаты для трех публичных доменов;
- достаточно места для одновременно работающих образов и резервной копии.

Схема базы данных изменяется только командой `npm run migration:up`. API запускается с
`synchronize: false` и не меняет таблицы самостоятельно.

## Обычный деплой

```bash
./deploy.sh
```

Сценарий последовательно:

1. помечает текущие образы тегом `rollback`;
2. собирает API, админку и публичный сайт, не трогая работающие контейнеры;
3. сохраняет PostgreSQL и volume изображений в `./backups/<UTC timestamp>`;
4. запускает транзакционные миграции в отдельном контейнере;
5. заменяет API и ждет его healthcheck;
6. заменяет фронтенды и ждет их healthcheck;
7. запускает smoke-тест публичных страниц и API.

Если ошибка возникает после начала обновления контейнеров, сценарий автоматически
возвращает приложения на образы с тегом `rollback`. Миграции автоматически назад не
откатываются: каждый релиз должен соблюдать `expand -> migrate -> contract`, поэтому
предыдущая версия приложения остается совместимой с расширенной схемой.

Для полноценной проверки входа перед деплоем можно передать учетные данные только в
окружении процесса:

```bash
SMOKE_ADMIN_NAME=admin SMOKE_ADMIN_PASSWORD='...' ./deploy.sh
```

Без них smoke-тест проверит доступность страницы входа, но не отправит пароль.

## Авторизация администратора

Админка использует единственную сессию администратора в cookie `admin_session` со
свойствами `HttpOnly`, `Secure` и `SameSite=Strict`. JWT недоступен JavaScript-коду и
не сохраняется в `localStorage`. Закрытые API endpoints на каждом запросе проверяют
подпись и срок JWT, роль `admin`, существование администратора в БД и версию его
пароля. После смены пароля прежние сессии перестают действовать.

Доступны только четыре auth endpoint:

- `POST /auth/login`;
- `GET /auth/profile`;
- `PUT /auth/password`;
- `POST /auth/logout`.

Регистрация и `/user` удалены. Миграция `002-single-administrator` сохраняет заранее
выбранную внутреннюю запись администратора и удаляет остальные учетные записи только
после создания backup. Если выбранная запись отсутствует или больше не является
администратором, deployment останавливается до изменения данных.

Пять неудачных попыток входа с одного IP блокируют новые попытки на 15 минут. CORS
разрешен только доменам из `CORS_ORIGINS`; production Compose задает публичный сайт и
админку.

## Типы инструментов: релиз 2A

Миграция `003-tool-types-expand` создаёт справочник `tool_types`, добавляет nullable
поле `tools.tool_type_id` и переносит в справочник уникальные значения прежнего поля
`tools.tool_type`. Миграция завершается ошибкой, если хотя бы один существующий
инструмент не получил связь.

Во время переходного релиза API сохраняет оба представления: строку `tool_type` для
старых клиентов и `tool_type_id` вместе с объектом `toolType` для новых. Изменение
названия типа синхронно обновляет старую строку у связанных инструментов. Удалить
используемый тип нельзя. Старую колонку разрешено удалять только отдельным релизом 2B
после проверки всех клиентов на production.

## CI/CD

Каждый из трех приложений собирается своим CI workflow при push и pull request.
Корневой репозиторий дополнительно проверяет shell-скрипты, Compose и сборку всех
production-образов.

Production-операции запускаются вручную из workflow `Production operations` в
репозитории `monino-tools-user`. Доступны три режима:

- `audit` — read-only отчет о сервере;
- `verify` — сборка релиза, backup текущих данных и проверка миграции/приложений на
  временных volumes без переключения production;
- `deploy` — передача собранного из `main` релиза на VPS и запуск `deploy.sh`.

Workflow использует GitHub Environment `production` и не запускается автоматически
при push. Одновременно может выполняться только одна production-операция.

Для проверки реального login/profile/logout добавьте `SMOKE_ADMIN_NAME` и
`SMOKE_ADMIN_PASSWORD` в secrets GitHub Environment `production` репозитория
`monino-tools-user`. Workflow передает их только окружению SSH-процесса; в release и
`.env` они не записываются.

Submodule всегда обновляются до коммитов, зафиксированных корневым репозиторием.
Использование `git submodule update --remote` в deployment запрещено.
GitHub Runner передает готовое дерево релиза на VPS, поэтому production-серверу не
нужны GitHub credentials. Успешные релизы сохраняются в
`/root/monino-tools-releases`, а `/root/monino-tools-current` указывает на текущий.

## Резервные копии

Создать резервную копию отдельно:

```bash
./create-backup.sh
```

Путь можно изменить через `BACKUP_ROOT`. В каталоге копии находятся:

- `postgres.dump` — custom-format dump с инструкцией создания БД;
- `static-data.tar.gz` — содержимое `/app/static`;
- `compose.yml` без подстановки секретов и `git-revision.txt`;
- `SHA256SUMS` для проверки целостности.

Копии из `./backups` необходимо дополнительно отправлять во внешнее хранилище. Копия
на том же сервере не защищает от отказа диска.

## Откат приложения

Вернуть предыдущие образы без изменения данных:

```bash
./rollback.sh
./smoke-test.sh
```

Это основной способ отката. Он безопасен для additive-миграций. Команду
`npm run migration:down` следует применять вручную только для миграции, у которой явно
реализован безопасный `down`; baseline намеренно запрещает автоматический откат.

## Полное восстановление данных

Операция заменяет текущую БД и все изображения:

```bash
RESTORE_CONFIRM=yes ./restore-backup.sh ./backups/20260902T120000Z
./smoke-test.sh
```

Перед восстановлением сценарий проверяет контрольные суммы и останавливает три
приложения. PostgreSQL остается запущенным, затем контейнеры стартуют снова.

## Ручные проверки

```bash
docker compose ps
docker compose run --rm --no-deps api npm run migration:status
./smoke-test.sh
```

Логи проблемного сервиса:

```bash
docker compose logs --tail=200 api
```

## Решение по blue-green

На текущем одном сервере полноценный blue-green не вводится. Сборка, backup и
миграция выполняются при работающей старой версии; краткая недоступность возможна лишь
при замене API-контейнера. Для текущей нагрузки это проще и достаточно, а ошибки
сборки или миграции не останавливают сайт. Blue-green стоит добавить при требовании
нулевого downtime, наличии двух экземпляров API и внешнем балансировщике с readiness
переключением.
