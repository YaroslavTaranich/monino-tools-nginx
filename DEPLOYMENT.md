# Деплой и восстановление Monino Tools

## Требования

- Docker с Compose v2;
- заполненный `.env` на основе `.env.example`;
- DNS и сертификаты для трех публичных доменов;
- достаточно места для одновременно работающих образов и резервной копии.

Схема базы данных изменяется только командой `npm run migration:up`. API запускается с
`synchronize: false` и не меняет таблицы самостоятельно.

## Обычный деплой

```bash
./deploy.sh
```

Сценарий последовательно:

1. помечает текущие образы тегом `rollback`;
2. собирает API, админку и публичный сайт, не трогая работающие контейнеры;
3. сохраняет PostgreSQL и volume изображений в `./backups/<UTC timestamp>`;
4. запускает транзакционные миграции в отдельном контейнере;
5. заменяет API и ждет его healthcheck;
6. заменяет фронтенды и ждет их healthcheck;
7. запускает smoke-тест публичных страниц и API.

Если ошибка возникает после начала обновления контейнеров, сценарий автоматически
возвращает приложения на образы с тегом `rollback`. Миграции автоматически назад не
откатываются: каждый релиз должен соблюдать `expand -> migrate -> contract`, поэтому
предыдущая версия приложения остается совместимой с расширенной схемой.

Для полноценной проверки входа перед деплоем можно передать учетные данные только в
окружении процесса:

```bash
SMOKE_ADMIN_NAME=admin SMOKE_ADMIN_PASSWORD='...' ./deploy.sh
```

Без них smoke-тест проверит доступность страницы входа, но не отправит пароль.

## Авторизация администратора

Админка использует единственную сессию администратора в cookie `admin_session` со
свойствами `HttpOnly`, `Secure` и `SameSite=Strict`. JWT недоступен JavaScript-коду и
не сохраняется в `localStorage`. Закрытые API endpoints на каждом запросе проверяют
подпись и срок JWT, роль `admin`, существование администратора в БД и версию его
пароля. После смены пароля прежние сессии перестают действовать.

Доступны только четыре auth endpoint:

- `POST /auth/login`;
- `GET /auth/profile`;
- `PUT /auth/password`;
- `POST /auth/logout`.

Регистрация и `/user` удалены. Миграция `002-single-administrator` сохраняет заранее
выбранную внутреннюю запись администратора и удаляет остальные учетные записи только
после создания backup. Если выбранная запись отсутствует или больше не является
администратором, deployment останавливается до изменения данных.

Пять неудачных попыток входа с одного IP блокируют новые попытки на 15 минут. CORS
разрешен только доменам из `CORS_ORIGINS`; production Compose задает публичный сайт и
админку.

## Типы инструментов: этап 2

Миграция `003-tool-types-expand` создаёт справочник `tool_types`, добавляет nullable
поле `tools.tool_type_id` и переносит в справочник уникальные значения прежнего поля
`tools.tool_type`. Миграция завершается ошибкой, если хотя бы один существующий
инструмент не получил связь.

Переходный релиз 2A временно сохранял строку `tool_type` для старых клиентов вместе с
`tool_type_id` и объектом `toolType`. После обновления клиентов Release 2B был
развёрнут двумя совместимыми поставками: миграция `005-relax-legacy-tool-type`
подготовила безопасный rollback, а `006-finalize-tool-types` сделала
`tools.tool_type_id` обязательным и удалила старую колонку `tools.tool_type`.

Текущий API использует только `tool_type_id` и объект `toolType`. Удалить тип,
назначенный хотя бы одному инструменту, нельзя. Smoke-тест проверяет отсутствие старой
колонки непосредственно через `information_schema` и целостность всех связей в API.

## CI/CD

Каждый из трех приложений собирается своим CI workflow при push и pull request.
Корневой репозиторий дополнительно проверяет shell-скрипты, Compose и сборку всех
production-образов.

Production-операции запускаются вручную из workflow `Production operations` в
репозитории `monino-tools-user`. Доступны три режима:

- `audit` — read-only отчет о сервере;
- `verify` — сборка релиза, backup текущих данных и проверка миграции/приложений на
  временных volumes без переключения production;
- `deploy` — передача собранного из `main` релиза на VPS и запуск `deploy.sh`.

Workflow использует GitHub Environment `production` и не запускается автоматически
при push. Одновременно может выполняться только одна production-операция.

Для проверки реального login/profile/logout добавьте `SMOKE_ADMIN_NAME` и
`SMOKE_ADMIN_PASSWORD` в secrets GitHub Environment `production` репозитория
`monino-tools-user`. Workflow передает их только окружению SSH-процесса; в release и
`.env` они не записываются.

Submodule всегда обновляются до коммитов, зафиксированных корневым репозиторием.
Использование `git submodule update --remote` в deployment запрещено.
GitHub Runner передает готовое дерево релиза на VPS, поэтому production-серверу не
нужны GitHub credentials. Успешные релизы сохраняются в
`/root/monino-tools-releases`, а `/root/monino-tools-current` указывает на текущий.

## Резервные копии

Создать резервную копию отдельно:

```bash
./create-backup.sh
```

Путь можно изменить через `BACKUP_ROOT`. В каталоге копии находятся:

- `postgres.dump` — custom-format dump с инструкцией создания БД;
- `static-data.tar.gz` — содержимое `/app/static`;
- `compose.yml` без подстановки секретов и `git-revision.txt`;
- `SHA256SUMS` для проверки целостности.

После создания сценарий автоматически проверяет контрольные суммы, структуру дампа
PostgreSQL и безопасность путей в архиве изображений. Незавершённая или повреждённая
копия удаляется и не используется при деплое.

Полный цикл резервного копирования и восстановления проверяется в CI на изолированных
БД и Docker volume командой `./test-backup-restore.sh`. Тест не подключается к
production volumes.

## Очистка потерянных изображений

Посмотреть файлы, на которые больше не ссылаются категории, legacy-обложки или
`tool_images`:

```bash
docker compose run --rm --no-deps api npm run images:cleanup
```

Удалить найденные файлы:

```bash
docker compose run --rm --no-deps api npm run images:cleanup -- --delete
```

По умолчанию файлы моложе 24 часов сохраняются, чтобы очистка не конфликтовала с
текущей загрузкой. Порог задаётся переменной `IMAGE_CLEANUP_MIN_AGE_HOURS`. Deploy
создаёт и проверяет backup, применяет миграции, затем автоматически запускает очистку
с порогом 24 часа. Полный preview/delete цикл отдельно проверяется в CI на временных
БД и volume командой `./test-image-cleanup.sh`.

Копии из `./backups` необходимо дополнительно отправлять во внешнее хранилище. Копия
на том же сервере не защищает от отказа диска.

## Откат приложения

Вернуть предыдущие образы без изменения данных:

```bash
./rollback.sh
./smoke-test.sh
```

Это основной способ отката. Он безопасен для additive-миграций. Команду
`npm run migration:down` следует применять вручную только для миграции, у которой явно
реализован безопасный `down`; baseline намеренно запрещает автоматический откат.

## Полное восстановление данных

Операция заменяет текущую БД и все изображения:

```bash
RESTORE_CONFIRM=yes ./restore-backup.sh ./backups/20260902T120000Z
./smoke-test.sh
```

Перед восстановлением сценарий проверяет контрольные суммы, структуру дампа и пути в
архиве, затем останавливает три приложения. Изображения сначала распаковываются во
временный каталог внутри volume; текущие файлы заменяются только после успешной
распаковки. PostgreSQL остается запущенным, затем контейнеры стартуют снова.

## Ручные проверки

```bash
docker compose ps
docker compose run --rm --no-deps api npm run migration:status
./smoke-test.sh
```

Логи проблемного сервиса:

```bash
docker compose logs --tail=200 api
```

## Решение по blue-green

На текущем одном сервере полноценный blue-green не вводится. Сборка, backup и
миграция выполняются при работающей старой версии; краткая недоступность возможна лишь
при замене API-контейнера. Для текущей нагрузки это проще и достаточно, а ошибки
сборки или миграции не останавливают сайт. Blue-green стоит добавить при требовании
нулевого downtime, наличии двух экземпляров API и внешнем балансировщике с readiness
переключением.


## Этап 3: дополнения для аренды (развёрнут 8 сентября 2026 года)

Миграция `007-tool-accessories` добавляет `tools.accessory_only` с default `false`
и таблицу двусторонних связей. Существующие инструменты сохраняют прежние условия.
Порядок релиза: backup, миграция, API, админка и пользовательский сайт.
Новые API-поля аддитивны; старые запросы без `related_tool_ids` сохраняют связи.
Запрос с пустым массивом удаляет связи с обеих сторон. Смена назначения позиции
с несовместимыми связями отклоняется атомарно; сначала удалите такие связи в форме.

После развёртывания всех приложений назначьте дополнениям условие «Только с основным
инструментом», собственную цену и совместимое оборудование в админке. Не включайте
ограничения аренды до обновления публичного сайта: предыдущая версия их не показывает.
Откат на старый сайт после настройки дополнений тоже скрывает условия аренды;
такой откат требует согласованного восстановления предыдущего состояния каталога.
`migration:down` намеренно запрещён, чтобы не терять ограничения аренды и связи.

Проверки перед релизом:

- `cd api && npm run build && npm test -- --runInBand`
- `cd admin && npm run build`
- `cd user && node --test utils/calculate-price.test.cjs && npm run build`
- Интеграционный тест требует отдельную пустую локальную PostgreSQL 15, порт 55439,
  БД `monino_accessories_test`, пользователя `postgres` и тестовый пароль
  `accessories-test-only`. Из `api` выполнить `node test/tool-accessories.integration.cjs`.
  Тест применяет все миграции к тестовым данным и проверяет симметрию, независимую
  сортировку, отсутствие транзитивных связей, ограничения SQL, откат ошибочных
  изменений, каскадное удаление и совместимость старых запросов.

Smoke после релиза: создать дополнение и связать с двумя основными инструментами;
проверить обе стороны, тарифы, порядок, удаление связи и сохранение после перезагрузки.
Одна связь не должна автоматически связывать два дополнения между собой.

## Этап 4: совместимый API галереи

Миграция `008-tool-images` создаёт таблицу `tool_images` и переносит каждое текущее
`tools.image` в неё как обложку. До перевода обоих фронтендов API продолжает возвращать
`tools.image`, а старый `POST /tools/:id/image` обновляет ту же обложку в новой таблице.

Новый API поддерживает до пяти фотографий инструмента, множественную загрузку,
сортировку, удаление и выбор обложки. Загруженные JPEG, PNG и WebP проверяются по
содержимому, уменьшаются до 2000 пикселей, сохраняются как WebP без EXIF и остаются в
постоянном volume `static-data`.

Релиз `e461a6e` развёрнут 9 сентября 2026 года workflow
https://github.com/YaroslavTaranich/monino-tools-user/actions/runs/34336711130.
Production workflow, миграция и smoke-тест завершились успешно. Дополнительная
проверка публичного API подтвердила восемь инструментов, восемь перенесённых
фотографий и совпадение каждой новой обложки с legacy-полем `image`.

### Галерея в админке

Админка использует новый API галереи: позволяет загрузить несколько JPEG, PNG или
WebP, изменить порядок перетаскиванием, выбрать обложку, открыть превью и удалить
фотографию. Интерфейс показывает прогресс загрузки, ограничение в пять изображений
и ошибки API. Для категорий сохранён прежний компонент одиночной фотографии.

### Галерея на пользовательском сайте

Обложка остаётся в верхнем блоке инструмента и используется в каталоге и Open Graph.
Если у инструмента есть дополнительные фотографии, сайт показывает их отдельной
секцией. Основной кадр секции имеет горизонтальное соотношение `3:2` и заполняется с
обрезкой через `object-fit: cover`; миниатюры переключают кадр. Полноразмерная
модалка сохраняет фотографию целиком и поддерживает кнопки, клавиши со стрелками,
Escape и свайп на мобильных устройствах.
